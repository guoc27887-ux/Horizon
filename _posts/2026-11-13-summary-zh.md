### [Rust 1.100 稳定 never type、自定义分配器并改进 Cargo 依赖管理](https://blog.rust-lang.org/2026/11/12/Rust-1.100.0/) ⭐️ 9.0/10

Rust 1.100 已于 2026 年 11 月 12 日发布，稳定了长期开发中的 never type 和自定义分配器等语言特性。Cargo 侧引入了“依赖冷却期”（minimum publish age / dependency cooldowns，RFC 3923）：配置后，解析器会忽略比设定时间更新的发布版本，除非该版本已写入 Cargo.lock。该版本还默认让 cargo::unused\_dependencies 以 warn 级别报告未使用的依赖，并使 cargo-install 默认使用 .crate 压缩包内已有的 lockfile，--locked 因此变为无操作。官方博客未在摘要材料中给出完整发布说明或性能数据。

hackernews · mbStavola · 11月12日 18:39 · [社区讨论](https://news.ycombinator.com/item?id=50472038)

**「背景」** Rust 1.100 是 Rust 语言的第 100 个稳定版本。此前，never type（类型 \!）长期处于不稳定状态，自定义分配器支持也一直受限，因此这次稳定化对长期等待这些能力的开发者具有直接意义。

**「对开发者的实际影响」** Rust 1.100 让开发者可以直接在稳定版中使用 never type、自定义分配器等长期特性，并可通过 Cargo 的依赖冷却与未使用依赖警告改进依赖管理。团队若希望降低供应链风险，可配置 min-publish-age，让解析器忽略过新发布的版本，除非这些版本已在 Cargo.lock 中；同时可利用默认开启的 cargo::unused\_dependencies 警告清理 Cargo.toml。

**「社区讨论」** 评论者 nirinor 列举了 never type、自定义分配器、依赖冷却期和 cargo-install lockfile 行为变化；n\_u 对 Cargo 默认警告未使用依赖表示欢迎。ammar\_az 指出还有 bool::toggle\(\)、Box::map\(\)、str::trim\_prefix\(\)/trim\_suffix\(\)、Path::trim\_prefix\(\) 等稳定 API 未在博客中提及；steveklabnik 称这是“里程碑式发布”。jadbox 则询问编译速度是否提升，并抱怨日常需要 cargo clean 清理约 90GB 临时文件，这属于个人体验，来源内容未提供编译性能结论。

### [PostgreSQL 22 年历史类型混淆漏洞被升级为服务器代码执行](https://mehmetince.net/part-3-6-how-i-ended-up-turning-a-22-year-old-postgresql-type-confusion-primitive-into-rce-cve-2026-6460/) ⭐️ 8.0/10

安全研究人员 Mehmet Ince 发布技术报告，称将 PostgreSQL 一个存在约 22 年的类型混淆问题（编号 CVE-2026-6460）从底层原语逐步利用为服务器上的代码执行。报告描述了 PostgreSQL 内部 Datum 值与类型标识分离、类型混淆以及后续利用链的构造过程。社区评论指出，这类利用需要先拥有数据库账号并通过 SQL 访问数据库，因此更准确的定性是已认证环境下的权限提升，而不是无需认证的远程代码执行；对多租户数据库环境风险更大。

hackernews · ozirus · 11月12日 18:22 · [社区讨论](https://news.ycombinator.com/item?id=50471761)

**「背景」** PostgreSQL 的 Datum 是数据库内部用来传递 SQL 值的表示形式，其类型信息由单独的类型标识符维护；当类型标识与实际内存表示不一致时，就会发生类型混淆。CVE-2026-6460 正源于对这类带类型值跟踪不足：拥有创建或修改数据库对象权限的已认证用户，可通过 ALTER ... SET DATA TYPE 等 DDL 操作触发混淆，使数据库进程以运行数据库的操作系统用户身份执行任意代码。PostgreSQL 官方安全公告与 Red Hat 的漏洞描述均将其定性为需要对象创建/修改权限的提权类问题，而非无需认证的远程代码执行。

**「实际影响」** 对运行 PostgreSQL 的组织而言，CVE-2026-6460 的主要风险在于：拥有创建或修改数据库对象权限的认证用户，可通过 ALTER ... SET DATA TYPE 等特定 DDL 命令触发类型混淆，并以运行数据库进程的操作系统用户身份执行任意代码，从而从数据库账号越权到主机层面。Red Hat 的公告也确认了这一前提：需要具备创建或修改数据库对象的权限，而非匿名远程利用。因此，多租户数据库、把不可信用户授予 DDL 权限、或数据库账号与高价值主机权限未分离的环境风险最高。运维上应尽快升级到包含修复的版本（如 PostgreSQL 18.7），并收紧对象创建/修改权限；同时注意 PostgreSQL 14 已达生命周期终点，继续使用将缺少安全修复。

**「社区讨论」** 评论者 logophobia 和 jmuguy 认为，这更像是从数据库账号权限提升到整个服务器权限的攻击，称其为“远程代码执行”会夸大危险程度。其他评论则称赞作者公开了发现零日漏洞的完整思路，并认为文章对理解数据库内部机制很有价值。
