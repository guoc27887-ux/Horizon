### [Rust 1.100 Stabilizes Never Type, Custom Allocators, and Cargo Improvements](https://blog.rust-lang.org/2026/11/12/Rust-1.100.0/) ⭐️ 9.0/10

Rust 1.100 was released on November 12, 2026, stabilizing two long-awaited language features: the never type and custom allocators. The release also brings Cargo dependency-management changes, including configurable minimum publish ages known as dependency cooldowns, warnings for unused dependencies enabled by default, and a change so that cargo install uses the lockfile included in the .crate tarball by default, making --locked a no-op. Community commenters also noted additional stabilized standard-library APIs, such as bool::toggle\(\), Box::map\(\), and string/path trimming methods, though the supplied source does not include the complete release notes or performance measurements.

hackernews · mbStavola · Nov 12, 18:39 · [Discussion](https://news.ycombinator.com/item?id=50472038)

**「Background」** Rust is a systems programming language whose releases are coordinated through the Rust compiler and Cargo, its package manager and build tool. Rust 1.100 is a notable round-number release because it stabilizes several long-running experimental features, including the never type and the allocator API, while adding Cargo controls such as dependency cooldowns, unused-dependency warnings, and lockfile-aware \`cargo install\` behavior.

**「Impact」** For Rust developers, the practical effect is that Cargo now warns about unused dependencies by default through the \`cargo::unused\_dependencies\` lint, and teams can configure a minimum publish age—dependency cooldowns—so the resolver ignores versions published too recently unless they are already in Cargo.lock. \`cargo install\` also uses the existing lockfile in the \`.crate\` tarball by default, making \`--locked\` a no-op. Developers using \`never\` or custom allocators can now rely on those features on stable, but should check their code and Cargo configuration against the new defaults before upgrading.

**「Community reaction」** Commenters broadly welcomed the release, with nirinor highlighting never type, custom allocators, dependency cooldowns under RFC 3923, and the cargo-install lockfile change, and steveklabnik calling it a monumental release for long-term features. ammar\_az argued the release is large enough that the blog post omits several useful stabilized APIs, while jadbox asked whether compilation is faster and complained about needing daily cargo clean runs to clear roughly 90 GB of temporary files; those performance concerns are user reports, not established release measurements.

### [PostgreSQL type-confusion bug turned into server code execution](https://mehmetince.net/part-3-6-how-i-ended-up-turning-a-22-year-old-postgresql-type-confusion-primitive-into-rce-cve-2026-6460/) ⭐️ 8.0/10

Security researcher Mehmet Ince published a technical write-up describing how he turned a 22-year-old PostgreSQL type-confusion primitive into server-side code execution, tracked as CVE-2026-6460. The article walks through the exploitation path from a database-level bug to control over the server process. Community discussion emphasized that the technique requires an authenticated database session, so it is best understood as authenticated privilege escalation from a database account to the underlying server rather than unauthenticated remote code execution. The write-up is valuable mainly for its detailed look at PostgreSQL internals and the researcher&\#x27;s exploitation process.

hackernews · ozirus · Nov 12, 18:22 · [Discussion](https://news.ycombinator.com/item?id=50471761)

**「Background」** PostgreSQL stores values internally as Datum, a generic representation whose interpretation depends on a separate type identifier, so a mismatch between the stored bytes and the expected type can cause the database to treat non-pointer data as a pointer. CVE-2026-6460 arises from inadequate tracking of typed values across data-definition operations such as ALTER TABLE ... SET DATA TYPE, letting an authenticated user who can create or alter database objects trigger type confusion and execute code as the operating-system user running PostgreSQL. The exploit path discussed here is therefore best understood as privilege escalation from a database account to host-level code execution, rather than an unauthenticated remote-code-execution flaw.

**「Impact」** For organizations running multi-tenant or shared PostgreSQL deployments, CVE-2026-6460 means an authenticated database user who can create or alter objects—such as via ALTER ... SET DATA TYPE—may be able to execute arbitrary code as the operating-system user running the database, potentially escaping the database boundary to the host. Administrators should prioritize applying the PostgreSQL security update \(e.g., 18.7, which fixes this and many other code-execution flaws\), review which accounts hold DDL privileges, and restrict object-creation/alteration rights in shared environments; note that PostgreSQL 14 has reached end of life, so unsupported deployments face heightened risk. The exploit requires an authenticated database context rather than unauthenticated remote access, so exposure is greatest where untrusted users can run DDL.

**「Community discussion」** Commenters logophobia and jmuguy argued that the issue should be described as privilege escalation rather than unauthenticated RCE, because the exploits require access through a database account; logophobia added that this is mostly a concern for multi-tenant database environments. Other readers, including igbanam, amluto, and sailfast, praised the write-up for explaining the path to the zero-day and the relevant PostgreSQL internals.
